# MHA module-level golden I/O (inner ComplexMHA datapath)

Per-module reference I/O for the **inner** MHA datapath that `layer_io_fp32/` does
NOT contain (it only has the outer `mattn.input_proj` / `mattn.output_proj`,
because those are `nn.Module`s caught by forward hooks; everything below lives
inside the free function `complexLayers._mha_attention_forward`).

Generated by `scripts/dump_mha_module_io.py` from the **same deploy ckpt + same
golden wav** as the shipped golden. Faithfulness is proven end-to-end: with the
capture patch installed, the model output waveform equals
`layer_io_fp32/output_waveform.fp32.hex` **bit-exactly** (max_abs_diff = 0).

- ckpt: `strict_core_pow2_blockfloat_deploy_ep3_vctk0.8357_timit0.7898.ckpt`
- wav : `p225_p225_009_az-40_snr+0.0.wav`
- dims: `embed_dim=256, num_heads=16, head_dim=16, T=399`, sliding window = 32 keys.

## Complex / tied handling (read first)

The MHA is **weight-tied** (`tied_mha=true`): a single real attention block `M`
is run twice — once on the real part and once on the imaginary part of the
complex MHA input `x = x_r + i·x_i`:

```
a = M(x_r)        ->  real_pass/   (this folder)
b = M(x_i)        ->  imag_pass/
ComplexMHA(x) = (a - b) + i·(a + b)
```

So `real_pass/` and `imag_pass/` use the **same weights**; they differ only in
the input half. The `(a-b, a+b)` recombination happens in `MultiheadAttention`'s
caller, *after* `out_proj` — it is NOT inside this datapath.

## Representative slice

One frame is dumped in full: query `t* = 351` (the "newest" query of the
chunk-aligned block `[320..351]`, so its 32-key causal window is complete).
Block tensors cover the 32 queries `[320..351]`. All 16 heads are dumped.

`local_idx` convention: `local_idx = query_frame − key_frame`, range `0..31`
(`local_idx 0` = the query's own frame / newest key; `local_idx 31` = oldest).
The hardware packet stores `local_idx` (5-bit). Files suffixed `_localidx` are
ordered by `local_idx` ascending (so they line up across scores / K / V / probs).

## ⚠️ Sliding-window vs the square `[32×32]` block

The model uses a **true sliding window** (query `t` attends to keys
`[t−31, t]`), so a single dense `[32×32]` `Q_block·K_blockᵀ` is exact **only for
the last row** (query `t*=351`, whose window is exactly `[320..351]`). Earlier
rows `r<31` of the dense block are missing their cross-block keys
`[t−31 .. 319]`, which the `mask_block` zeroes inside this tile. For complete,
per-query data use the `qstar_*` (single newest query) files — those are exact.
The hardware QK chunk actually computes `q[320:352] · k[289:352]ᵀ` (63 keys) then
bands to `local_idx∈[0,31]`; the square block is the in-block sub-tile.

## Numeric path (deploy)

- QKᵀ: **L-Mul m8 (bit-exact)**, windowed (chunk=32, window=32). This folder's QK
  uses the deploy **fp32-sum** accumulate (round once). For the HW **fp16 adder-tree**
  accumulate (round every add, matches CE `adder_tree_fp16`) see the sibling folder
  `../mha_module_io_fp16tree/` and `docs/MHA_GOLDEN_HANDOFF_2026-06-08.md` Part C.
- Scale: **×2⁻²** (pow2; `1/√head_dim = 1/√16 = 1/4`).
- Mask: additive `-inf` outside the causal sliding window.
- Softmax: `shift_topk_pow2_clamp8_nomantissa` with top-4 — output is dense with
  ≤4 nonzero, weights are pow2 fractions normalized by a pow2 denominator.
- Packet: top-4, `prob_scale=256` (q0.8, 8-bit code, max 255), `local_idx` 5-bit.
- Score×V: **L-Mul m8 (bit-exact)** over the 4 packet slots · V (`score_v_mode=lmul`).
- out_proj: `F.linear` (W4A16 — input is the fp16 Score×V accumulator).
